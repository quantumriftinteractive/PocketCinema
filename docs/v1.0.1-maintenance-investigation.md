## Compatibility investigation: correction proposed, not implemented

The release's classifier requests codec/profile/geometry but not `pix_fmt`,
`bits_per_raw_sample`, or H.264 level. Its H.264 confirmation condition does not
constrain profile or chroma format. Synthetic High 4:4:4 Predictive/yuv444p at
320x240 with AAC is incorrectly labeled confirmed/direct. This establishes an
overly broad confirmation policy, not the cause of the reporter's audio-only case.

Actual player build evidence:

- `release-sources/miyoo/ffmpeg-2.4.14-pocketcinema/configuration/config.h`
  enables native H.264, swscale, and disables the listed hardware H.264 backends.
- The preserved corresponding-source ZIP contains `ffmpeg-2.4.14.tar.xz`.
  Upstream `libavcodec/h264.c:1264` accepts bit depths 8 through 14 except
  11 and 13; `h264_ps.c:370` accepts chroma format IDs through 3, and
  `h264_ps.c:630` rejects invalid/unimplemented bit depths. This shows native
  decoder paths broader than 8-bit 4:2:0, not complete profile support or a
  guarantee that all those paths work in this built binary on this device.
- Upstream `ffplay.c:1535`, `1652`, and `1782` use SDL YV12 and conversion/filter
  output YUV420p. Source capability is not physical acceptance.
- `docs/real-stream-resolution.md` records Constrained Baseline/yuv420p;
  `docs/series-episode-browsing.md` records High/yuv420p; and
  `docs/bounded-transcoding.md` records Main direct playback and the accepted
  bounded Main level 3.0, yuv420p conversion output. There is no comparable
  physical matrix for 4:2:2, 4:4:4, monochrome, or higher-bit-depth direct play.

Proposed smallest follow-up, requiring approval and focused validation:

1. Request and normalize `pix_fmt`, bit depth, and level from FFprobe.
2. Confirm direct H.264 only inside the measured geometry/rate/bitrate/audio
   envelope with 8-bit yuv420p and measured Baseline/Main/High profile families.
   Resolve aliases and absent metadata explicitly rather than guessing.
3. Route unmeasured chroma/bit-depth/profile combinations through the existing
   bounded yuv420p converter, subject to existing geometry/tool restrictions.
   Verify FFmpeg can decode each proposed input before promising conversion.
4. Version or invalidate persisted compatibility entries lacking the new fields;
   otherwise seven-day cached results bypass corrected classification.
5. Add probe/decision/cache tests and focused physical direct/conversion checks.

No classifier, cache semantics, or converter change is included in this branch.
The exact complete profile/pixel-format support matrix remains unmeasured.

- Client logs selected stream/audio identifiers, compatibility status/message,
  `playback conversion=...`, server seek, player launch and exit.
- Full FFplay diagnostic output is appended to the current UI log; it can show
  decoded codec/pixel format, decoder errors, and SDL/audio initialization.
- SDL video readiness, startup time, watched time, pause tracking, exit status,
  and sanitized playback-failure classification already exist.
- Server conversion startup/interruption and bounded sanitized stderr diagnostics
  already distinguish download/start/no-output failure stages.

identifiers and URLs: redact private URLs, query tokens, account values, and
