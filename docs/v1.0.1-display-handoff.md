## Evidence and hypothesis

Upstream OnionOS 4.3.1-1 infoPanel calls SDL_InitDefault(false), initializes SDL
video, sets a 640x480 hardware surface, and presents with SDL_Flip. It retains
that backend while waiting for dismissal and calls SDL_Quit on exit. At the
developer's 4.4.0-beta2 revision f11f7a0d, the Miyoo infoPanel path uses a software
surface and direct framebuffer writes instead of SDL video initialization.
Both implementations render then wait for the same /tmp/dismiss_info_panel flag;
neither continually repaints during that persistent wait. Both remove the flag
on observing it. Their display teardown differs.

Sources:

- [4.3.1-1 infoPanel](https://github.com/OnionUI/Onion/blob/v4.3.1-1/src/infoPanel/infoPanel.c)
- [4.3.1-1 SDL initialization](https://github.com/OnionUI/Onion/blob/v4.3.1-1/src/common/utils/sdl_init.h)
- [beta infoPanel](https://github.com/OnionUI/Onion/blob/f11f7a0d/src/infoPanel/infoPanel.c)
- [beta direct-framebuffer helper](https://github.com/OnionUI/Onion/blob/f11f7a0d/src/common/utils/sdl_direct_fb.h)
- [upstream comparison](https://github.com/OnionUI/Onion/compare/v4.3.1-1...f11f7a0d)

v1.0.0 launches FFplay while the panel is alive and dismisses it only after
finding a vendor SDL_SetVideoMode diagnostic in FFplay output. Overlapping
initialization or later SDL teardown could interfere with FFplay on 4.3.1-1.
That is a compatibility hypothesis, not a reproduced root cause. A visible
preparation image does not prove a live overlay is hiding working video. Video,
filter, SDL-library or readiness-diagnostic failure remains possible.

The current safety corrections below supersede the initial implementation and
151-test result recorded here. The original investigation and earlier result
remain historical evidence.

## Initial implementation and visible behavior (superseded by safety review)

The preparation panel remains through stream checks, subtitle discovery,
PocketCinema Server session creation and subtitle-package download. At entry to
play_url, after those operations, the client dismisses and reaps its owned panel
before launching FFplay or its resource monitor. Playback readiness no longer
controls panel lifetime. Both app-local and stock-player paths use the handoff.

stop_loading permits three one-second polls for graceful dismissal. If the
panel remains, it sends TERM to that PID and polls for two more seconds, then
KILL and one final second. It calls wait only once the PID is no longer alive.
It never signals unrelated panels by name. A forced shutdown at handoff aborts
that playback attempt with a concise logged/displayed preparation-screen error. If even KILL
cannot end the owned process, it logs the PID and exits the UI rather than
starting another SDL screen. Ownership is retained for a bounded cleanup retry;
an uninterruptible kernel task cannot be guaranteed to disappear. Each stop
attempt has at most six one-second sleeps, excluding scheduling overhead.
Cancellation can invoke another bounded stop attempt from EXIT cleanup.
The flag is cleared after each stop attempt. A new loading panel is not started
when stopping the previous one fails.

Polling can add up to one second to an ordinary panel shutdown. After dismissal,
users may see a temporary black screen, or the last preparation image until
FFplay clears/replaces it, while remote media/player startup continues. This gap
has no artificial readiness timeout. Its actual appearance/duration is unmeasured
on either OnionOS version for this candidate. Startup is still excluded from
Continue Watching; panel exit does not start watched-time or pause tracking.

The existing SDL_SetVideoMode readiness/validity checks, pause monitoring,
FFplay command, stdout/stderr capture and playback-failure classification remain.
The vendor diagnostic is still an unresolved dependency. This change does not
claim a first-frame acknowledgment or fix missing diagnostics. It does not
change subtitles, transcoding, server APIs, streams, settings or player binaries.
No OnionOS core changes are required.

### Identity and target compatibility

Each launch records its actual parent shell PID and the child's Linux procfs
start-time field (stat field 22), paired with the child PID. The shell reads its
own /proc/self/stat directly: $$ alone cannot identify command-substitution
shells. The parser strips the final ') ' after comm, validates the PID, field
count, parent/start-time numbers and process-state character, and handles comm
containing spaces and parentheses. Start times are compared as strings, avoiding
32-bit shell arithmetic overflow.

The required procfs layout is checked at runtime before starting a preparation
panel or player. A missing/unreadable/malformed layout fails closed; no ps,
pidof, readlink, timeout, pidfd, new runtime or new target utility is assumed.
Every TERM/KILL and every cleanup retry rereads identity. An absent process or
matching zombie permits wait on the original child; a live process with a
missing, changed or unreadable identity permits neither signal nor wait.
An already exited child is accepted only when the shell's wait returns zero;
unknown/non-child status (127), crashes and nonzero exits fail the handoff.

This is the safest practical procfs/builtin-kill approach in the current shell
client, not an atomic kernel process handle. The original process can exit and
its PID can be reused between the final identity read and kill. Rechecking
immediately before each signal greatly narrows that race but cannot eliminate
it. Same-PID/parent/start-tick collisions and launch-registration races are also
not mathematically excluded. No claim of pidfd availability or target-side
identity validation is made. Before physical acceptance, confirm the runtime
probe passes on both actual OnionOS versions; neither was accessed here.

### Failure propagation and orderly teardown

The initial three-second graceful, two-second TERM, one-second KILL budgets
remain. Shutdown results now distinguish clean exit (including already exited),
abnormal exit with recorded status, forced exit, unverifiable identity, and a
process still alive after deadlines. Only a clean panel exit authorizes a display
handoff. Forced death does not establish SDL teardown even when the PID is gone.
If identity becomes unverifiable, signaling stops instead of escalating blindly.

Every stop_loading caller now aborts on failure except EXIT cleanup, which logs
and continues bounded resource cleanup. A failure is latched in shell state and
an app-session temporary file shared with command substitutions. New loading
panels, selectors, QR screens, messages and FFplay check that latch. It cannot be
silently cleared by starting another panel. Only root UI exit clears the session
file; a command substitution cannot clear its parent's failure. Timed messages
now use the same owned panel lifecycle instead of a separate unbounded wait.

For an unsafe display state the client logs the cause and prints a concise error
to stderr, then exits; it deliberately does not create another SDL error panel.
OnionOS may return to Home, or stale preparation pixels may remain until another
renderer takes over. The exact user-visible failure outcome is unmeasured.
The ordinary successful path still permits a black/stale preparation image
between dismissal and first video; readiness, watched-time and pause gates remain.

### Cancellation and diagnostics

run_ffplay is now an asynchronous brace function ending in exec, so the tracked
background PID is FFplay itself rather than a surviving wrapper. The player,
playback-control, pause and resource helpers record identities. Cancellation
ignores repeated termination signals during bounded cleanup, stops verified
owned processes, and waits only after terminal state is established. Normal
helper shutdown uses the same bounds; uncertain/live helper shutdown aborts the
UI and suppresses progress. The existing top-level server-status monitor also
gets a bounded identity-checked stop so EXIT does not retain its old unbounded
wait; route selection and its network behavior are unchanged.

FFplay stdout/stderr are appended before temporary-log deletion on cancellation.
If the player remains alive or unverifiable, the current output is copied and
the temporary log is retained for diagnosis. Successful normal completion still
classifies the existing FFplay log, retains exit status and excludes startup from
watched time. A zero pause-monitor exit and valid result file are still required
for valid pause tracking. Seek-restart signals are identity-checked too.

An uninterruptible or unverifiable process cannot be guaranteed stopped. The
client refuses to signal an unknown process and reports that limitation rather
than claiming complete cleanup. SIGKILL cannot execute SDL_Quit; whether forced
termination leaves problematic framebuffer state on 4.3.1-1 remains unmeasured.
The upstream dismissal file remains global: identity checks protect signals but
do not turn Onion's flag into a process-specific protocol. Concurrent unrelated
infoPanels can still interfere with consumption of that global flag.
